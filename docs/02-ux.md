# Yoga Center Attendance Management App — UX

## Purpose
UX source of truth after Product Requirements. Defines Information Architecture, roles, key user flows, UX relationships, important UX patterns, and Figma planning. Product requirements remain in `01-product.md`.

`01-product.md` is the product source of truth. This document translates those requirements into UX structure and flows. If a product requirement changes, this document must be updated accordingly.

#### Navigation terminology note

**"Assigned Classes" is the authoritative navigation label.**

Some wireframe screens show an inconsistent **"My Classes"** label for the same
destination. That is a wireframe inconsistency, not an approved change. Do not
rename the navigation item because of it, and do not introduce "My Classes" as
a second concept.

## Core UX Relationships

```text
Student
   │
   ├───────────────┐
   ↓               ↓
Membership      Enrollment
                   │
             ┌─────┴─────┐
             ↓           ↓
          Batch A      Batch B
             │           │
             └─────┬─────┘
                   ↓
              Schedule
                   ↓
             Class Session
                   ↓
              Attendance
```

Attendance eligibility:

```text
Active Batch Enrollment
          +
Active Membership on Session Date
          ↓
Eligible for Attendance
```

Membership alone does not make a student eligible for a particular batch.

Historical attendance remains associated with the original class session even when membership, enrollment, batch, or schedule information changes later.

#### Schedule screens
- The Schedule area has **two views**, switched by a toggle beneath the page
  heading: **Weekly Schedule** and **List View**. Both are approved and drawn
  in the wireframe, and both show the same recurring schedule records — the
  page heading, description and Add Schedule action stay the same across
  them. ("Weekly Schedule List View" in an extracted text rendering of the
  wireframe is those two toggle labels sitting side by side, not one label
  for the list.)
- **Weekly Schedule is the default view.** Opening the Schedule area with no
  view selected shows the week grid, as the Information Architecture above
  states ("Weekly Schedule ← Default"); List View is reached through the
  toggle. Phase 13 shipped with the List View as the default, which
  contradicts the approved IA; correcting that default is a Phase 13
  follow-up and changes nothing else about either view.
- The **Weekly Schedule** view is a week grid: a Today action, week-by-week
  navigation, the current week's date range, Monday–Sunday columns headed by
  their dates, and an hour-by-hour time axis down the side. Each recurring
  schedule appears as a card placed at its weekday and start time, showing
  the batch short code, the time range, and the instructor.
- The Weekly Schedule view **visualises recurring schedule records only**. It
  reads the same schedules the List View reads and lays them out by weekday
  and time. It does not create, store or modify class sessions, and it
  carries no session status, attendance, or exception behaviour — those
  belong to later phases.
- The **List View** is the tabular view: Batch, Day, Time, Instructor,
  Effective From, Effective Until, Status and Action columns, with the
  Batch / Instructor / Status filters, search, and pagination.
- Schedule Details keeps **both** the Overview and Recurring Pattern tabs as
  drawn, even though they repeat several fields. The overlap is the approved
  layout, not an error to tidy away.
- Schedule Details' **Upcoming Sessions** tab is a read-only projection of
  the recurring pattern across its effective period. It displays future
  occurrences; it does not create, store, or modify them.
- Batch Details' **Schedules** tab lists the recurring schedules for that one
  batch and offers Add Schedule, as drawn in the wireframe.
- **Add Schedule, Edit Schedule, and Deactivate Schedule have no dedicated
  approved wireframes.** They are composed from already-approved UX patterns —
  the Students/Batches form layout, and Review → Confirm → Save for edit and
  deactivation (Flows 04 and 05) — rather than derived from a new wireframe
  screen. This mirrors the composed Membership screens noted above.

#### Weekly Schedule view — week navigation
The wireframe draws a Today action and the current week's date range. The
navigation controls that make them meaningful are settled here:

- A **Today** button returns the grid to the week containing the current date.
- A **Previous week** and a **Next week** button move the grid one week at a
  time.
- The **current week's date range** is displayed alongside them.
- Navigation changes **only which week is displayed**. It loads no new kind of
  record and changes nothing stored.
- There is no month view and no day view.

#### Weekly Schedule view — time axis
The wireframe draws a partial time axis only (its sample runs from 6 AM to
early afternoon), which is not enough to implement against. The following is
an **explicit decision resolving that ambiguity**, not a reading of the
wireframe:

- The grid begins at **6:00 AM** and extends through **10:00 PM**.
- Time labels are at **one-hour** intervals.
- The range is **fixed**. It must not expand, contract or shift based on which
  schedules happen to exist.
- **Vertical scrolling** is allowed when the full range does not fit the
  viewport.
- Each schedule card is positioned by its **weekday and its start and end
  time**.

#### Weekly Schedule view — overlapping schedules
V1 deliberately permits overlapping schedules for both a batch and an
instructor (`01-product.md` §12), so two cards can occupy the same weekday and
time. The wireframe draws no such case. The following is an **explicit
decision resolving that ambiguity**, not a reading of the wireframe:

- Overlapping schedules **remain visible**. None is hidden, collapsed or
  summarised, and there is no "+N more" affordance.
- Overlapping cards are rendered **side by side** within the same weekday and
  time area.
- The grid is **display-only**: no drag-to-reschedule, and no resizing a card
  to change its time.
- The grid performs **no conflict prevention or warning**. The rules in
  `01-product.md` §12 that allow overlapping schedules are unchanged; showing
  an overlap is not the same as blocking one.

#### Session-level flows belong to a later phase
Flows 06 (Change One Specific Session) and 07 (Cancel / Holiday) both start
from the Schedule area, but they act on an individual class session rather
than on a recurring schedule. Class Sessions are a separate phase from
Schedule (see `04-development-plan.md` §5), so these two flows are delivered
with Class Sessions, not with the Schedule screens above.

Both flows also **materialize** the session they act on: an occurrence that
was until then only projected from the recurring pattern becomes a stored
record at that moment, snapshotting its batch, instructor, date and time
(`01-product.md` §7A). Neither flow has a dedicated approved wireframe, so
both are composed from already-approved patterns — the existing form layout
plus Review → Confirm → Save, exactly as the Membership and Schedule screens
were.

#### Class Session screens
The class-session surface lives under the **Attendance** navigation item, as
the Information Architecture above sets out — not under Schedule:

```text
Attendance
├── Today's Sessions      ← Default
├── All Sessions
└── Session Details
    ├── Overview
    ├── Eligible Students
    └── Attendance
```

- **Today's Sessions** is the default view: today's date in the heading, and
  a row per session with Time, Batch, Instructor and Status.
- **All Sessions** adds Date and its own filters — search by batch or
  instructor, a date range, Batch, Instructor and Session Status — plus
  pagination.
- **Session Details** shows the session's own Information panel: batch,
  date, time, instructor and status.
- Both lists and Session Details show sessions whether or not they have been
  materialized — a projected occurrence and a stored one look the same to the
  admin, which is the point (`01-product.md` §7A).
- **Edit This Session** (Flow 06) is reached from Session Details, not from
  the Schedule area Flow 06's own diagram starts in ("Weekly Schedule /
  Upcoming Sessions") — Session Details is the one place that already
  addresses a specific occurrence, materialized or not, so it is the entry
  point that actually works for both. The action only appears when the
  session displays as Upcoming.
- **Mark Cancelled / Holiday** (Flow 07) is also reached from Session
  Details, as a single "Mark Cancelled / Holiday" action rather than two
  separate buttons — the status choice is one step inside the flow, not a
  fork in the entry point, matching the flow's own diagram ("Mark Session →
  Cancelled / Holiday"). It appears whenever the session's *stored* status
  is still scheduled, independent of whether it displays as Upcoming, In
  Progress, or Completed — deliberately different from Edit This Session's
  Upcoming-only rule, since a session that has not yet had attendance
  recorded can still be marked even after its class time has passed.
  Composed from the same Review → Confirm → Save pattern as every other
  flow with no dedicated wireframe.

These screens are **shared between two phases**. Class Sessions delivers the
lists, the Session Information panel, and the session-level flows above.
Everything attendance-shaped on the same screens arrives with Attendance: the
Eligible Students column, the Attendance column and its Present/Absent
counts, the Attendance Summary panel on Overview, the Eligible Students and
Attendance tabs, and the Take Attendance / View Attendance actions. Until
then those elements follow the same honest-placeholder treatment used for the
Student and Batch panels in earlier phases — shown in their approved position,
stating plainly that the data is not available yet, rather than fabricated or
silently dropped.

#### Add Membership entry points
Three entry points reach Membership Details:
- Memberships list → Add Membership (Flow 14, includes Select Student)
- Student Details → Add Membership (Flow 14 variant, student already known)
- Add Student guided flow → Step 2 Membership (Flow 02, no Review/Confirm)

#### Memberships list filters
- Plan, Payment Status, and Membership Status filter their respective fields.
- From Date / To Date both filter Membership Start Date: From Date = start
  date on or after the selected date; To Date = start date on or before the
  selected date.
- The Membership filter (here and on the Students list) distinguishes three
  states: Active, Expired, and None (no membership record). Expired is not
  equivalent to None.

#### Membership wireframe reference conflicts
The approved Student ID format remains YC-000001 (01-product.md §12). Do not
implement the wireframe's STU-0001 or YC-2025-089 student ID examples — both
are wireframe inconsistencies, not approved changes, the same category as the
"My Classes" label conflict above.

The wireframe's MEM-0001 / MEM-0921 membership ID examples are visual
references only. The approved format is MEM-000001, matching Student ID's
digit count and generation pattern.

## Important UX Patterns

### Status Separation
Keep these concepts independent in the UX:

- **Attendance:** Present / Absent
- **Membership:** Upcoming / Active / Expired / Cancelled
- **Payment:** Paid / Pending
- **Class Session:** Upcoming / In Progress / Completed / Cancelled / Holiday

Do not use payment status as a substitute for membership status, attendance status, or class-session status.



### Review Before Important Changes
Use:
```text
Edit → Review → Confirm → Save
```
for recurring schedule changes, one-session exceptions, cancellation/holiday, and attendance corrections.

### Protect Historical Data
Make it clear when a change affects future records only. Past attendance must not be silently changed by:
- membership expiry or renewal
- student batch changes or leaving a batch
- student deactivation
- batch deactivation
- recurring schedule changes
- future session changes or cancellation.

### Fast Attendance
Primary instructor path:
```text
Dashboard → Today's Class → Take Attendance
```

### Avoid Duplication
Use contextual entry points without creating duplicate concepts:
- Student attendance from Student Details
- Batch schedules from Batch Details
- Session attendance from Attendance
- Historical records from Attendance History
- Summaries from Reports

### Global Shell: User Identity Placement

Approved implementation decision for the global application shell:

- The signed-in user's identity (name + role) appears in the **global Header**,
  in the top-right account menu.
- The **Sidebar footer contains Logout only.**
- Do **not** duplicate the user profile in the Sidebar.

Some wireframe screens show the user's name and role repeated at the bottom of
the Sidebar alongside Logout. That duplication is superseded by the decision
above. Do not reintroduce it when implementing or extending the shell.

### Login: visual-reference caution

`docs/ui-reference/login.png` is a visual/composition reference only. It shows
**Remember me**, **Google Sign-In** and a **Light/Dark theme toggle**, none of
which are approved V1 functionality in `01-product.md` or this document.

Do not implement those elements from the reference image. See the "Known
reference conflict: `login.png`" section in `CLAUDE.md`.

## UX Principles
1. Operational first — prioritize frequent admin/instructor actions.
2. Simple attendance — V1 is Present/Absent only.
3. Flexible scheduling — add, change, deactivate, or make one-time exceptions.
4. Historical integrity — future changes must not damage past records.
5. Clear relationships — Student, Membership, Enrollment, Batch, Schedule, Session, Attendance remain distinct.
6. Guided setup — new student and batch setup guide the Admin through required steps.
7. Role clarity — Admin has full access; Instructor has focused access.
8. Don't overbuild — add complexity only for a real requirement.
